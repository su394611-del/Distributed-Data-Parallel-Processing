02 / SYSTEM ARCHITECTURE

From launch to synchronized weights.

The pipeline below follows the implementation's control flow. DDP is data parallelism: workers use different data, while each keeps the complete model.

01 / LAUNCHtorchrun

Starts worker processes and provides rank metadata.

02 / CONNECTProcess group

Initializes Gloo or NCCL as appropriate.

03 / SHARDData sampler

Assigns training examples to each rank.

04 / TRAINForward & loss

Computes next-token loss on local batches.

05 / SYNCDDP gradients

Coordinates gradient reduction during backward.

06 / SAVERank zero

Writes model checkpoint or adapters to disk.

i
DDP replicates; it does not combine GPU memory.

Two 4 GB GPUs do not create an 8 GB memory pool for one model. For models that do not fit on one device, look into FSDP, tensor parallelism, or other forms of model sharding. The code here is an example of DDP, not those other strategies.

03 / TWO TRAINING PATHS

One orchestration pattern, two models.

The same distributed launch concepts are exercised with a tiny model and a pretrained Qwen checkpoint.

PATH A / NO MODEL DOWNLOAD

Tiny causal Transformer

Train a small byte-level autoregressive model with learned token and positional embeddings, one Transformer encoder block with causal masking, and a next-token training objective.

  • Runs on CPU without a pretrained-model download
  • Can demonstrate two ranks with Gloo
  • Uses a small built-in corpus or a text file
  • Writes tiny_transformer.pt on rank zero
PATH B / CUDA-ORIENTED

Qwen2.5 + LoRA

Load Qwen/Qwen2.5-0.5B-Instruct and configure PEFT LoRA adapters for parameter-efficient next-token training on the provided text corpus.

  • Adapter targets: q_proj and v_proj
  • LoRA rank 8, alpha 16, dropout 0.05
  • Runs with one GPU or multiple CUDA workers where supported
  • Saves adapters and tokenizer from rank zero

Before you run

  1. Install: use Python 3.12 and the dependency list in the repo.
  2. CPU first: run the two-rank Gloo command without any Hugging Face download.
  3. Inspect output: check worker ranks, global batch, loss logs and the saved checkpoint.
  4. GPU next: install a CUDA-enabled PyTorch build matching your platform and driver.
  5. Qwen: launch one rank per available GPU, with enough memory per device.

The GitHub README has notebook instructions, custom-corpus flags, version and hardware notes. The Qwen workflow does not use 4-bit QLoRA; it uses LoRA on a pretrained model.

Scope and validation

This is an educational distributed-training implementation, not a production model-serving service. The README reports local PyTorch CPU checks, including a two-process Gloo test, but does not establish physical multi-GPU Qwen performance, quality metrics or production fault tolerance. Dataset size, evaluation splits, reproducibility controls, observability and memory planning would need further work for production training.

07 / FAQ

Distributed training, explained.

Is DDP the same as tensor parallelism?

No. DDP gives each rank a complete model replica and divides the dataset. Tensor parallelism partitions parts of the model across devices. DDP does not pool VRAM.

Can I demonstrate distributed training on a CPU-only PC?

Yes. The script and README include a two-process CPU command using the Gloo communication backend. It is suitable for learning the process-group and gradient synchronization mechanics.

Is Qwen2.5 trained from scratch in this project?

No. The Qwen path downloads a pretrained Qwen2.5-0.5B-Instruct checkpoint and applies parameter-efficient LoRA updates. The tiny causal Transformer is the model constructed from scratch.

Is this QLoRA or 4-bit quantization?

No. The repository explicitly identifies the Qwen training path as LoRA, without 4-bit QLoRA quantization.

What does the global batch size mean?

For this example, global batch size equals the per-rank batch size multiplied by the number of ranks. The implementation does not include gradient accumulation.
